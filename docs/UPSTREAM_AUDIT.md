## 范围

- 审计日期：2026-08-23
- 版本：`0.8.10`
- 检查对象：全部发布文件、CLI 与 setup 实现、测试、安装元数据、进程启动、文件修改、网络调用、会话迁移和凭据处理。
- 验证：上游 `npm test` 在审计快照通过。

静态审计没有发现隐藏的令牌上传、模型流量中继、远程控制后门、安装期脚本或混淆载荷。这不是对未来提交或所有运行环境“绝对无后门”的证明。

## 数据与网络路径

1. ChatGPT 账号额度查询通过本机官方 `codex app-server` 的 `account/rateLimits/read` 完成。
2. API-key 模式允许用户提供任意 `openai_base_url`，验证时会向该地址发送 API key。该行为有文档说明，但与“只使用官方登录”的安全目标不符。
3. 包没有运行时 npm 依赖，也没有 `preinstall`/`postinstall` 脚本。
4. 账号启动使用 `spawn` 参数数组，没有启用 shell；未发现基于参数的直接 shell 注入。
5. 工具会读取 `auth.json` 并解析 JWT 以显示邮箱、判断过期与选择账号；未发现把读取结果发送到项目自身服务器的代码。

## 发现

### 高：默认绕过 Codex 审批与沙箱

普通 `cx` 运行会默认添加 `--dangerously-bypass-approvals-and-sandbox`，只有显式 `--no-bypass` 才保留官方安全边界。多账号工具不应改变执行授权模型。

`cab`：永不自动添加安全覆盖参数。

### 高：默认自动信任项目

工具默认把当前目录写入每个账号的 `config.toml`，设置 `trust_level = "trusted"`；可选 PATH wrapper 也会这样做。这可能在用户未审查仓库时扩大执行权限。

`cab`：不修改 `config.toml` 或项目 trust。

### 高：自动跨账号披露上下文

额度触发后，工具可复制中断会话到另一个账号并自动恢复。历史提示、工具输出和工作区信息因此进入另一个账号的数据边界，默认流程中缺少逐次确认。

`cab`：不探测额度、不自动换号；共享会话必须双重确认，恢复账号由用户显式指定。

### 中：支持任意第三方 API 终端

API-key setup 可把密钥发送到用户提供的 OpenAI-compatible 地址。URL 可能是恶意地址或误配置地址。

`cab`：不支持 API key、base URL 或代理配置，只调用官方登录命令。

### 中：`--full` 共享 SQLite、WAL 和日志

多个 Codex 实例共享 `state_5.sqlite`、目标/记忆数据库及 WAL 文件，存在竞争、状态污染和损坏风险。上游文档有并发警告，但选项仍容易被使用。

`cab`：只允许共享 `sessions/`；数据库、WAL、日志、配置和凭据永久排除。

### 中：自动激活 blocked 目标

恢复逻辑会把 `blocked`、`paused` 或 `usageLimited` 目标改回 active。`blocked` 不一定代表额度限制，自动覆盖可能违背原工作流状态。

`cab`：不调用内部目标状态 API。

### 中：文件写入的符号链接与权限加固不足

部分配置/认证写入会跟随既有符号链接；`mode: 0600` 对已经存在的文件不必然收紧权限。账号目录创建也依赖进程 umask。

`cab`：拒绝配置和账号目录符号链接，原子替换配置并在每次保存后强制 `0600`，目录强制 `0700`，从不写 `auth.json`。

### 低：更新与成熟度风险

项目规模和维护者数量较小，直接从 GitHub 的可变分支全局安装，缺少签名发布与固定校验和。代码短小且无运行时依赖是积极因素。

`cab`：提供无依赖 Go 单文件构建、本地跨平台构建脚本和 SHA-256；未来发布应固定 tag 与 commit。

## 保留的合理设计

- 每个账号使用独立 `CODEX_HOME`。
- 登录交给官方 Codex CLI。
- `auth.json` 不在账号之间建立链接。
- 子进程参数不通过 shell 拼接。
- 修改前创建可恢复备份，并提供 dry-run/活动进程保护的思路。

## 结论

审计快照没有发现后门，但安全默认值不符合本项目的威胁模型。`cab` 采用独立 Go 实现，只保留隔离 `CODEX_HOME` 和调用官方 CLI 的基本机制，不复制 GPL 源码。
